# Archive cockpit and CLI gRPC boundaries

`oskal cockpit` is a read-only archive inventory. It shows only explicitly selected
or actually archived subjects; it does not invent a default workload. Archived
counts describe stored envelopes, including signed or adverse material. Without
an authoritative contract, pinned producer verification and live source eligibility,
standing remains UNKNOWN and verified evidence remains zero. Coherence, freshness,
authority, current evidence root and semantic drift remain UNKNOWN. The display
claims no provider identity, live enforcement, performance, or reconciliation.

Opening the archive does not create directories. Missing or corrupt stores return
errors before a frame is published, preserving the affected files for diagnosis.
An empty valid archive produces no invented rows. The cockpit does not implement
a configurable live-assessment mode.

## TLS client

Every network gRPC command requires both an explicit CA bundle and the exact
expected DNS name or IP SAN. The client does not infer trust from loopback or use
plaintext when TLS configuration is absent. For example, with operator-provided
certificate files and a server certificate for `server.oskal.test`:

```sh
oskal assurance state k8s://example/Pod/workload \
  --server 127.0.0.1:9090 \
  --tls-ca-file ca.pem \
  --tls-server-name server.oskal.test
```

For mutual TLS, add the matching certificate/key pair:

```sh
oskal assurance state k8s://example/Pod/workload \
  --server 127.0.0.1:9090 \
  --tls-ca-file ca.pem \
  --tls-server-name server.oskal.test \
  --tls-client-cert-file client.pem \
  --tls-client-key-file client.key
```

Wrong server SANs, untrusted CAs, missing paired files and invalid certificates fail.
No plaintext bypass flag is provided.

## Standalone server

The server validates its actual certificate/key pair, certificate role and validity,
and optional client CA before binding a network listener. All TLS files are bounded
to 1 MiB. TLS 1.3 is the minimum. Start the unconfigured, UNKNOWN assessment service:

```sh
oskal serve --port 9090 \
  --tls-cert-file server.pem --tls-key-file server.key
```

To require authenticated client certificates, add `--tls-client-ca-file ca.pem`.
This CA authorizes peers to this unconfigured service; it does not grant live
assessment, workload identity, evidence admission, or execution capability.
Submitted observations remain bounded, unverified process-local metadata.
Health RPCs report service availability, not assurance standing. Connections,
streams, message sizes and shutdown time are bounded. Static certificate/CA files
are loaded at startup; rotation requires a restart. Buffered unverified observations
are not durable across that restart.

No certificate or signing identity is generated by `serve`. The separate HTTP
SPIFFE authentication and CapabilityLease path is unchanged. Live configured
assessment remains the responsibility of the authenticated controller/service
assembly, not this standalone archive service.

## Verification

`go test -race ./cmd/oskal -run 'TestActualCLIRequiresVerifiedTLS|TestActualCLIMutualTLSAndPairValidation' -count=1 -v`
executes the built CLI as real subprocesses against its actual TCP/TLS listeners.
It checks missing TLS denial, exact server-name validation, trusted/untrusted CAs,
plaintext denial, mutual TLS acceptance/rejection, matching key pairs, size bounds,
and default UNKNOWN responses. The command forms above are exercised with actual
isolated test certificates, not mocked cryptography or backends.

Cockpit tests use filesystem CAS and genuine Ed25519 signatures, then corrupt a
fixture blob to verify error propagation and byte preservation. These checks need
no Kubernetes API, SPIRE process, VM changes, or Phase 2 attestation.

The full `go test -race ./...` suite and `golangci-lint run` passed for this change.
The existing HTTP SPIFFE/lease integration tests remain environment-gated; no live
HTTP or cluster proof was repeated during the concurrent demonstration.
